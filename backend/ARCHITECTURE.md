# ERP-Cafe Backend — Architecture & Structure

A multi-branch cafe ERP backend. **Spring Boot 4.1 · Java 21 · PostgreSQL + JPA/Hibernate · Flyway · Gradle (Kotlin DSL).**

---

## 1. Architecture at a glance

A **modular monolith**: one deployable app, one database, split into cohesive **modules** under `vn.essvn.erpcafe`. Each module owns a slice of the domain and exposes only a small published `api` package to the others.

**The golden rule:** a module may depend on another module *only* through its `api` package (a facade interface + DTOs). It must never import another module's `domain`, `persistence`, `application`, or `web` internals.

```
External client ──HTTP──▶  web (controllers)
                              │
Sibling module ──Java call──▶ api (facade)  ─▶ application (services) ─▶ persistence (repos) ─▶ DB
                                                       │
                                                    domain (entities)
```

## 3. The module layering convention

Every feature module follows the **same six-package shape**. Learn one, understand them all.

| Package | Contains | Rule |
|---|---|---|
| `api` | Facade interface + published DTOs + domain events | The **only** package other modules may import. No JPA types. |
| `web` | `@RestController`, request/response records, `@Valid` | Never returns entities; talks to `application`. |
| `application` | `@Service`, `@Transactional` business logic | The orchestration / rules layer. |
| `domain` | `@Entity`, enums, value objects | Depends on nothing outward (sits at the center). |
| `persistence` | Spring Data `JpaRepository` interfaces | DB access; implementations generated by Spring. |
| `mapper` | MapStruct entity ↔ DTO mappers | Generated at build time. |

## 4. Current modules

### `common` — shared kernel (depended on by all, depends on none)

```
common/
├── domain/
│   ├── BaseEntity.java          # UUID id + @Version (optimistic locking)
│   ├── AuditableEntity.java     # + createdAt/By, updatedAt/By (JPA auditing)
│   ├── BranchScopedEntity.java  # + branchId (for branch-scoped modules, later phases)
│   └── Money.java               # BigDecimal + currency value object (never use double for money)
├── web/
│   ├── GlobalExceptionHandler.java  # @RestControllerAdvice → RFC 7807 ProblemDetail
│   ├── PageResponse.java            # stable paged-response envelope
│   └── ApiVersions.java             # "/api/v1" constant
├── exception/
│   ├── ResourceNotFoundException.java  # → HTTP 404
│   ├── BusinessRuleException.java      # → HTTP 422
│   └── ConflictException.java          # → HTTP 409
└── context/
    ├── BranchContext.java          # request-scoped active branch (thread-local)
    └── BranchContextFilter.java    # reads X-Branch-Id header (enforcement added in Phase 1)
```

### `config` — application wiring

```
config/
├── JpaConfig.java      # @EnableJpaAuditing + AuditorAware (currently "system"; real user in Phase 1)
└── OpenApiConfig.java  # Swagger UI metadata (/swagger-ui.html)
```

### `organization` — Company & Branch (the multi-branch backbone)

Defines the company → branch hierarchy. A **Branch's id is the `branch_id` that scopes all operational data** across the rest of the ERP, which is why this module comes first.

```
organization/
├── api/
│   ├── OrganizationApi.java   # facade for other modules (findBranch, branchExists)
│   └── BranchDto.java         # JPA-free branch view for cross-module use
├── web/
│   ├── CompanyController.java  # /api/v1/companies
│   ├── BranchController.java   # /api/v1/branches
│   ├── CompanyRequest.java / CompanyResponse.java
│   └── BranchRequest.java  / BranchResponse.java
├── application/
│   ├── CompanyService.java
│   └── BranchService.java      # implements OrganizationApi
├── domain/
│   ├── Company.java            # soft-deletable master data
│   └── Branch.java             # belongs to a Company; soft-deletable
├── persistence/
│   ├── CompanyRepository.java
│   └── BranchRepository.java
└── mapper/
    ├── CompanyMapper.java
    └── BranchMapper.java
```

## 5. Data flow (one request)

```
POST /api/v1/branches {json}
  → BranchController        (web)          validate @RequestBody with @Valid
  → BranchService.create()  (application)  business rules, @Transactional
  → BranchRepository.save() (persistence)  Hibernate INSERT; auditing fills created/updated
  → Branch                  (domain)       the entity persisted
  ← BranchMapper.toResponse (mapper)       Branch entity → BranchResponse DTO
  ← 201 Created + Location header + JSON body
```

**Three shapes of the same data**, each with a distinct audience:
- `*Request` (web) — what a client is allowed to send in.
- `*Entity`  (domain) — the rich internal model stored in the DB.
- `*Response` (web) — the safe view sent back to clients.
- `*Dto` (api) — the view handed to **other modules** (only created when a consumer needs it).

Entities never cross the web boundary; the mapper always converts to a DTO first.

## 6. Key conventions

- **Primary keys:** UUID (`@GeneratedValue(strategy = GenerationType.UUID)`), good for multi-branch and future service splits.
- **Money:** always `Money` / `BigDecimal` (`NUMERIC(19,4)`, HALF_EVEN). Never `double`/`float`.
- **Optimistic locking:** every entity has `@Version`; concurrent edits to the same row → `OptimisticLockingFailureException` → HTTP 409.
- **Soft delete:** master data (Company, Branch) uses Hibernate `@SQLDelete` + `@SQLRestriction("deleted = false")`. Transactional/financial records will never be soft-deleted (use status/void instead).
- **Auditing:** `@EnableJpaAuditing` fills created/updated columns automatically via `AuditorAware`.
- **Schema ownership:** **Flyway owns the schema** (`db/migration/V*.sql`); Hibernate is `ddl-auto: validate` (checks entities match, never alters).
- **Errors:** services throw domain exceptions; `GlobalExceptionHandler` maps them to RFC 7807 `ProblemDetail` responses.
- **API versioning:** URI-based `/api/v1` via `ApiVersions.V1`.
- **Branch scoping:** `branch_id` discriminator on branch-scoped entities; `BranchContext` resolves the active branch per request (enforcement lands in Phase 1).

## 7. Flyway migrations

- Location: `src/main/resources/db/migration`, single linear history.
- Naming: `V<phase>_<seq>__<description>.sql` — number ranges reserved per module so files sort by build phase:
  `V1` organization · `V2` identity · `V3` catalog · `V4` inventory · `V5` sales · `V6` staff · `V7` reporting.
- Migrations are immutable once applied (Flyway checksums them).

## 8. Module roadmap (built incrementally, each phase runnable)

- **Phase 0 — Foundation + Organization** ✅ — common kernel, config, Company/Branch CRUD.
- **Phase 1 — Identity & Auth** ✅ — Spring Security + JWT (access + refresh), users/roles/permissions (+ role permission management), per-branch access enforcement, real `AuditorAware`, bootstrap seeding.
- **Phase 2 — Catalog** ✅ — category, product (+ per-branch price), recipe/recipe-line, modifier groups + modifier recipe deltas, pricing, `CatalogApi`.
- **Phase 3 — Inventory & Purchasing** ✅ — ingredient, supplier, per-branch StockItem, append-only StockMovement ledger, moving-average costing, full purchase-order lifecycle + receiving, low-stock alerts; publishes `InventoryApi` (deduct + COGS, warn-but-allow negative, idempotent).
- **Phase 4 — Sales / POS** ✅ — order state machine (OPEN→PAID→COMPLETED, cancel/void/refund), line + modifier snapshots, split payments, line+order discounts and tax; completion explodes recipes → deducts stock + captures COGS (price − COGS = margin); void/refund return stock.
- **Phase 5 — Staff / HR & Shifts** ✅ — employee master data (deactivate, never delete), shift state machine (SCHEDULED→IN_PROGRESS→COMPLETED / cancel), clock in/out with hourly-rate snapshot at clock-in and labor cost captured at clock-out; `staff:clock` is a separate permission so cashiers punch in/out without editing the schedule; publishes `StaffApi` (labor cost per branch/period).
- **Phase 6 — Reporting** ✅ — `reporting` module owns no tables: it composes other modules' published APIs (`SalesApi` revenue aggregates, `InventoryApi.depletionCost` ledger-side COGS, `StaffApi.laborCost`, `OrganizationApi.listActiveBranches`). Endpoints: `/reports/summary`, `/reports/sales-by-day`, `/reports/outlets` (cross-branch comparison incl. labor vs sales), guarded by `report:read`. Two COGS views are reported side by side: order snapshots vs stock-ledger depletion.

## 9. Running locally

```bash
# 1. Start Postgres (host port 5433 to avoid clashing with other local stacks)
docker compose up -d

# 2. Run the app on the dev profile (port 8090)
./gradlew bootRun

# 3. Explore
#    Swagger UI:  http://localhost:8090/swagger-ui.html
#    Base URL:    http://localhost:8090/api/v1
```

**Local DB (dev only):** host `localhost`, port `5433`, db/user/password all `erpcafe`.
Production reads `DB_URL` / `DB_USER` / `DB_PASSWORD` from the environment instead.

**Authenticating (dev):** on first startup the app seeds a bootstrap admin.

```bash
# 1. Log in → returns { accessToken, refreshToken }
curl -X POST http://localhost:8090/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"admin@esscafe.vn","password":"admin1234"}'

# 2. Call protected endpoints with the access token
curl http://localhost:8090/api/v1/branches -H "Authorization: Bearer <accessToken>"

# 3. Act within a branch (branch-scoped requests)
curl http://localhost:8090/api/v1/branches \
  -H "Authorization: Bearer <accessToken>" -H "X-Branch-Id: <branchId>"
```

- Public endpoints: `/api/v1/auth/login`, `/auth/refresh`, `/auth/logout`, Swagger. Everything else needs a valid access token.
- Access tokens are short-lived JWTs (15 min); use `/auth/refresh` (rotates) for new ones; `/auth/logout` revokes a refresh token.
- Bootstrap admin credentials come from `app.security.bootstrap.*` (dev defaults in `application-dev.yml`; `ADMIN_EMAIL`/`ADMIN_PASSWORD` env vars in prod).
